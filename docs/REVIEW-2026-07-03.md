# Code Review — WebScrapingDinamico-Automatico

**Fecha:** 2026-07-03
**Tipo:** Auditoría integral del repo
**Stack:** NestJS 11 · Angular 22 · Chrome MV3 · Prisma 7 · PostgreSQL 16 · pnpm workspace

---

## TL;DR

El proyecto tiene **3 sistemas coexistiendo** y ninguno cerró el ciclo "automático" que el equipo buscaba:

1. **`pipeline/`** — CLI con Playwright headless. Cuando lo bloquean (captcha), cae a `quotes.toscrape.com` como respaldo. Es la auto-extracción original.
2. **`extension/`** — Mapeo visual + extracción en la sesión real del usuario. Es el enfoque "asistido" adoptado.
3. **App web** (backend NestJS + Angular) — UI, persistencia, scheduler.

Hay además **`docs/propuesta_integracion_pipeline.md`** que describe cómo conectar todo. **Nunca se implementó** — y es justo la pieza que devolvería el "automático" sin chocar con captchas.

El `PLAN.md` describe una realidad futura que NO coincide con el código actual: la mayoría de sus prioridades ya estaban listadas y casi ninguna está cerrada.

## 🔴 Críticos (atender primero)

### C1. Bug latente en `products.controller.ts`

```ts
@Get('domain/:domainRuleId')   // ← nunca se alcanza
@Get(':id')                    // ← matchea antes con id="domain"
```

Express resuelve por orden de registro. `GET /products/domain/abc` intenta `findOne('domain')` y devuelve 404. PLAN.md menciona este endpoint como faltante pero ya está y está **roto**. O reordenar o renombrar a `by-domain`.

**Archivo:** `backend/src/modules/products/products.controller.ts:43-65`

### C2. Cero autenticación + CORS abierto a extensiones

```ts
// backend/src/main.ts
if (/^(moz|chrome)-extension:\/\//.test(origin)) callback(null, true);
```

Cualquier extensión con permisos de red puede:

- `POST /products/ingest` y crear productos arbitrarios
- `POST /scraping-jobs` y encolar "trabajos" huérfanos
- `DELETE /domains/:id` y borrar reglas
- `PATCH /products/:id` (que ni existe — otro ítem del PLAN)

Aunque sea dev local, **esto no escala ni a staging ni a prod**. Mínimo: token esperado en header `X-Extension-Id` validado contra allowlist, o JWT por usuario.

**Archivo:** `backend/src/main.ts:7-21`

### C3. `ingestFromExtension` aplica una heurística que miente

```ts
// backend/src/modules/products/products.service.ts:ingestFromExtension
let title = 'Raw product';
for (const key of keys) {
  const v = String(product[key] ?? '').trim();
  if (v && v.length < 200 && !v.startsWith('http')) { title = v; break; }
}
```

Esto NO es "automático para cualquier página" — es **adivinar**. Si el primer campo que llega es el precio o un URL, el título queda mal. El extension YA sabe qué campo es cuál (vienen los nombres canónicos: `titulo`, `precio`, etc.). El backend ignora `fieldMappings` y re-adivina.

**Cambio mínimo:** que el extension mande `{ canonicalField, value }` por campo, o que el backend lea la regla y mapee. Hoy el `DomainRule` guardado con `fieldMappings` se desperdicia en este endpoint.

**Archivo:** `backend/src/modules/products/products.service.ts:118-175`

### C4. URL hardcodeada en el popup

```ts
// extension/src/popup/popup.ts:onExtract
fetch('http://localhost:3000/products/ingest', ...)
```

Sin env, sin abstracción. Si el backend cambia de puerto/host, hay que tocar el `.ts` y rebuildear.

**Fix:** `chrome.storage.local` con URL configurable desde UI, o `runtime.getURL('/config.json')`.

**Archivo:** `extension/src/popup/popup.ts:170-175`

## 🟠 Duplicación de UI (deuda UX seria)

Tenés **DOS visual-mappers funcionando en paralelo**:

### A. Popup de la extensión

- Archivo: `extension/src/popup/popup.html` + `popup.ts`
- Home view con field defs, mapping view, data view, CSV export
- Llama a `/products/ingest` directamente
- **Guarda reglas en `chrome.storage.local` (NO en el backend)**
- `GET_RULE`/`SAVE_RULE` manejados por el service worker

### B. Angular `visual-mapper.component`

- Archivo: `frontend/src/app/pages/visual-mapper/visual-mapper.component.ts`
- State machine completa: `idle → extension-mapping → mapping → saving → done → error`
- Se conecta a la extensión por `chrome.runtime.connectExternal` (port)
- Guarda reglas en el backend (`POST /domains`, `PATCH /domains/:id`)

**Consecuencia:** el usuario tiene dos formas de hacer lo mismo, **y los datos terminan en lugares distintos**. Una persona puede mapear en el popup y nunca ver esa regla en Angular, ni en `/products`. Datos huérfanos en `chrome.storage.local` para siempre.

**Recomendación:**

- **Matar el popup** (dejarlo solo con un botón "Open Visual Mapper" que mande un mensaje al SW para abrir Angular en nueva tab).
- O matar Angular y dejar el popup como única UI.
- Si ambos, sincronizá reglas vía `GET /domains?host=X` desde el popup. Hoy no se hace.

## 🟢 Mejoras estratégicas (donde hay valor real)

### S1. Resucitar el "automático" sin captcha

`docs/propuesta_integracion_pipeline.md` lo describe pero no se hizo. Tres opciones:

**Opción 1 — Mínimo (RECOMENDADA):** Replay automático en la extensión

- El popup mapea una página → regla persiste
- `chrome.alarms` dispara cada N horas/días → si el user tiene la página target abierta o la abre, la extensión scrapea automáticamente en background
- Sin captcha (sesión real del user)
- Sin servidor extra
- 2-3 días de trabajo

**Opción 2 — Medio:** `JobQueueService` en backend con WebSocket

- El extension se conecta al backend por WS
- Cuando el extension ve una URL target, scrapea y manda
- 1 semana

**Opción 3 — Alto:** `EtlModule` completo con Playwright embebido

- Para páginas públicas sin captcha (catálogos sin login)
- Reservar Playwright para eso, extensión para el resto
- 2-3 semanas

**Por qué Opción 1 es la correcta para este proyecto:** es la más fiel al principio "asistido = el user carga el captcha, después la extensión automatiza". Y es lo único que cabe en una entrega universitaria.

### S2. "Learning" del mapeo (diferenciador real)

Hoy cada vez que entrás a Temu, mapeás de cero. La regla se guarda por dominio pero **nunca se aplica sola**. Flujo ideal:

1. Usuario mapea Temu una vez → regla persiste
2. Usuario abre Temu de nuevo → **la extensión detecta el dominio, busca la regla, pregunta "¿quieres re-scrapear?"**
3. Si dice sí, scrapea en background y manda al backend

**Requiere:**

- Content script que al cargar consulte `GET /domains?host=<hostname>` (o lea de storage sincronizado)
- UI mínima en el popup: "Temu tiene una regla guardada · [Re-scrapear] [Editar]"

### S3. `fieldMappings` como única fuente de verdad

Hoy conviven `selectorTitle/Price/Image/Sku` (legacy) + `fieldMappings` (nuevo) en el mismo `DomainRule`. Es la peor combinación: dos formas de hacer lo mismo, una siempre desactualizada. Matar el legacy, hacer `fieldMappings` obligatorio, y que el backend **renderice el schema de la regla** a partir de `fieldMappings` (no al revés).

### S4. Robustez de la extracción

El `extractFieldsFrom` en `extension/src/content/mapper.ts` tiene un bug: si el campo se llama `precio`, parsea a float y sobreescribe. Pero si el campo se llama `titulo` y el contenido es "123", lo sobreescribe también. La heurística debería ser:

- Si el `canonicalField` matchea `/precio|price|amount/i` → `parseFloat`
- Si el `type` es `attribute` con `src`/`href` → URL
- En otro caso → string

**Archivo:** `extension/src/content/mapper.ts:368-392`

### S5. Validación real en el backend

El `ValidationPipe` global está bien (`whitelist: true, forbidNonWhitelisted: true`), pero:

- `domains.controller.ts:create()` recibe tipo inline — no hay DTO
- `products.controller.ts:POST` con `Record<string, unknown>` acepta cualquier cosa
- `products.service.ts:ingestFromExtension` no valida que `domain` exista ni que los productos tengan forma esperada

Tres DTOs a escribir: `CreateDomainDto`, `UpdateDomainDto`, `IngestProductsDto`. 30 min de laburo, sube mucho la calidad.

### S6. El handshake extension ↔ Angular

`extension.service.ts:available$` solo se setea en `true` la primera vez. Si la extensión se recarga (workflow de dev), Angular no se entera. Y si Angular carga antes que el content script, el `postMessage` inicial se pierde.

**Fix estándar:**

- Angular escucha `__VS_READY__` SIEMPRE (no solo la primera vez)
- Al cargar, hace ping + retry con backoff durante 3-5s
- Agregar un `chrome.runtime.sendMessage('PING')` con respuesta del SW como fallback

**Archivo:** `frontend/src/app/services/extension.service.ts:24-44`

### S7. Tests donde duele

Sin tests no podés refactorizar `ingestFromExtension` con confianza. Prioridad:

1. `extension/src/content/mapper.ts:extractFieldsFrom` y `extractProducts` — pura lógica, fácil con JSDOM
2. `backend/src/modules/products/products.service.ts:ingestFromExtension` con fixtures
3. `backend/src/modules/domains/domains.service.ts` CRUD
